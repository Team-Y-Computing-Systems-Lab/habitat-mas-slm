# Datasets, Inputs and Processing

Companion to [design.md](design.md).

## Current setup (since 2026-09-26): official Habitat data only

The project no longer uses EMOS's data or code. Everything comes from Habitat's official downloader
(`python -m habitat_sim.utils.datasets_download`) into one folder, `data/`:

| Download ID | What it gives us |
|---|---|
| `hssd-hab` | HSSD scenes (about 23 GB) |
| `hab3-episodes` | Habitat 3.0 HSSD rearrangement episodes: 37k train, 1,200 validation, two target objects each |
| `hab_fetch`, `hab_stretch`, `hab_spot_arm` | official robot models (URDF + meshes) |
| `ycb` | the task objects |
| `replica_cad_dataset`, `rearrange_dataset_v1` | ReplicaCAD scenes and rearrangement episodes (not used yet) |

The benchmark `hssd_fetch_stretch` (`mas/sim_host/configs/hssd_fetch_stretch.yaml`) runs the
`hab3-episodes` validation split with the official task spec `multi_agent_tidy_house`:
- the goal is both objects on their goal receptacles and both grippers empty;
- success is habitat's `pddl_success`;
- robot start positions are placed randomly by habitat (seeded) at least 5 m apart.

Instructions, the PDDL goal and the feasibility facts are generated by our pipeline, as described
below.

**Historical:** everything from section 1 onward describes the EMOS / Habitat-MAS data used until
2026-09-26. It's kept for the record. Results from that period are in `results/emos_fork_era/`.

## 1. Key findings

1. **All the HSSD and ReplicaCAD data is local and usable.** That's 34 HSSD scenes (23 GB) with
   their Habitat-MAS episodes, plus ReplicaCAD.
2. **MP3D is not usable yet.** `scene_datasets/mp3d` only points to the *example* scene
   (`17DRP5sb8fy`). None of the 27 scenes the MP3D episodes reference are on disk, so the
   multi-floor tasks (cross-floor navigation, multi-floor rearrangement) need the full Matterport3D
   download, which requires signing the Matterport Terms of Use.
3. **The episodes contain no language instruction and no plan.** They only give geometry: object
   poses, source and target receptacles, and robot line-ups (from `robots/robot_configs/`).
   The instruction, the PDDL goal and any failure or constraint settings have to be **generated by
   our pipeline** (§5). That is a chance to contribute something, not only a gap.
4. **Object and receptacle handles are hashes** (e.g. `e8dd67ee…_part_3_:0003`), which an SLM can't
   use. HSSD `metadata/` (`fpmodels-with-decomposed.csv`, `object_categories_filtered.csv`)
   maps them to names like "kitchen counter", so a naming step is required.

## 4. What an input to our system looks like

A raw Habitat-MAS episode is only geometry. We wrap it in an **episode spec**, which is the one
object that `mas/eval` loads. It has six parts. The first two come straight from existing data, the
next two are generated deterministically, and the last two are our scenario overlays.

```jsonc
{
  "spec_id": "hssd_height_man/0/ep0042/fleet-base/R0",
  "source": {                                      // (1) from Habitat-MAS
    "dataset": "hssd/0/hssd_height_man.json.gz",
    "episode_id": "42",
    "scene_id": "102344049"
  },
  "fleet": {                                       // (2) from robot_configs, then modified by us
    "initial": [
      {"id": "fetch_0",   "type": "FetchRobot_default",      "start_pos": [..], "start_rot": 0.03},
      {"id": "stretch_0", "type": "StretchRobot_head_only",  "start_pos": [..], "start_rot": 1.57}
    ],
    "events": [                                    // dynamic fleet (design §4a)
      {"step": 300, "op": "leave", "robot": "stretch_0"},
      {"step": 350, "op": "join",  "robot": {"id": "spot_0", "type": "SpotRobot_default", "start_pos": [..]}}
    ]
  },
  "instruction": {                                 // (3) generated (§5, P4)
    "text": "Put the foam brick on the high shelf in the living room and the soccer ball on the bedroom dresser.",
    "level": "explicit"                            // explicit | referential | underspecified
  },
  "ground_truth": {                                // (4) derived from targets / goal_receptacles
    "pddl_goal": "(and (on foam_brick_0 shelf_3) (on soccer_ball_0 dresser_2))",
    "oracle_plan_len": 8,                          // from the classical planner, used as a reference
    "entities": {"foam_brick_0": "061_foam_brick_:0000", "shelf_3": "e8dd67ee…_part_3_:0003"}
  },
  "resources": {                                   // (5) constraint scenario (design §7)
    "scenario": "R1-battery-tight",
    "battery_j": {"fetch_0": 1500, "stretch_0": 900},
    "slm": {"model": "qwen2.5-3b-instruct", "max_tokens_per_call": 512},
    "deadline_s": 120
  },
  "failures": [                                    // (6) failure injection (design §6)
    {"step": 120, "robot": "fetch_0", "skill": "pick", "code": "GRASP_FAIL"}
  ]
}
```

At runtime, the system receives **only**:
- `instruction.text`
- the fleet as **discovered through MCP** (never read directly from the spec)
- the observations it asks for through MCP tools and resources

`ground_truth`, `resources` and `failures` are used by the harness and the evaluator, never by the
agents. This keeps the evaluation honest.

## 5. Processing pipeline

### 5a. Offline: building the dataset (runs once, output is versioned)

```
Habitat-MAS episodes + robot_configs + scene metadata
   │
P1 Load & validate ── scene files exist? navmesh loads? robots place without collision? → drop bad episodes
   │
P2 Scene-graph extraction ── run the sim: floors, rooms, receptacles, objects, reachability → symbolic state
   │
P3 Naming ── hash handles → readable names (HSSD metadata / YCB names); de-duplicate ("shelf_3")
   │
P4 Instruction generation ── template from (object, source, goal) → optional SLM paraphrase;
   │                          3 levels: explicit / referential ("the ball near the sofa") / underspecified
   │
P5 Ground truth ── PDDL init + goal from targets/goal_receptacles;
   │                run the classical planner: solvable? oracle plan length? → drop unsolvable episodes
   │
P6 Variants ── fleet variants (base, +1 robot, −1 robot, capability swap, mid-episode join/leave)
   │           × resource scenarios (R0 none, R1–R6) × failure schedules (none, single, cascading)
   │
P7 Split & freeze ── dev (ReplicaCAD) / val / test (HSSD) → specs/*.jsonl + manifest (hashes, generator versions)
```

Checks to run on the frozen dataset:
- P4: a sample of generated instructions is checked by hand, e.g. 50 per level.
- P5: every kept episode has at least one valid plan with the base fleet.
- P6: for each "−1 robot" variant, record whether the task is **still solvable**. Unsolvable ones
  are kept on purpose and labelled, to test goal relaxation (design §6 level 5).

### 5b. Online: one episode at runtime

```
spec → Sim Host loads scene + robot pool → MCP servers register (fleet.initial)
     → Coordinator SLM: instruction + discovered skills/capabilities → PDDL goal + allocation
     → Classical planner → per-robot plans → Executor dispatches via MCP
     → harness applies fleet events / failures / resource drain at scheduled steps
     → Recovery Manager (retry → repair → reallocate → replan → relax)
     → episode ends: goal met, budget exhausted, or step limit
     → log: trajectory, every SLM call (tokens, latency), planner calls, recoveries, energy
```

### 5c. Evaluation

The trajectory logs are scored against `ground_truth` using these metrics:
- Success rate, and sub-goal success from the PDDL goal predicates
- Plan validity, and plan length relative to the oracle plan
- Recovery success and recovery depth
- Tokens, latency and energy

Results are aggregated by dataset, fleet variant, resource scenario and planner mode (P0–P3).

## 6. What this adds beyond EMOS's data

Habitat-MAS (reused as is): the scenes, object placements, heterogeneous robot line-ups and the
task categories.

Our additions, which are also a possible dataset contribution:
- Natural-language instructions at 3 levels of ambiguity
- A PDDL goal and oracle plan length for every episode
- Fleet-change variants, some of them deliberately unsolvable
- Failure-injection schedules
- Resource-constraint overlays
